# ClipboardPasteboardProbe

剪贴板取证探针：把"一次复制到底往剪贴板写了几次、每次写了什么"变成可复现的输出。

## 为什么单独做

插件落盘历史只能看到**结果**（"一次复制产生两条条目、相差 2 秒、第二条指向输入法缓存目录"），看不到**成因**。而要区分的两件事修法完全不同：

- **同一进程分两步写**（两次 `changeCount` 跳变间隔毫秒级）→ 短时间去抖就能合并；
- **另一个进程事后重写**（间隔秒级）→ 去抖窗口得拉到秒级，会吞掉用户真实的连续两次复制；只能改判据。

## 运行

```bash
./run.sh watch [秒]              只观察，自己去别的 App 复制
./run.sh copy <图片路径> [秒]     先把该图片写进剪贴板（fileURL + PNG 数据，与
                                 CleanShot / Finder 的复制同构），再继续观察
./run.sh compare <图A> <图B>      比对两份字节的「字节哈希」与「像素哈希」
```

单文件独立编译，只依赖系统 SDK，**不参与** NotchCenter 的 Tuist 构建。产物在 `.build/`。

注意 `copy` 模式会**改动你当前的剪贴板**（它就是在模拟一次复制），跑之前先存好手上的内容。

## 它已经回答过什么

2026-09-20 的实测（结论见 `docs/agent-notes/implemented/2026-09-20-clipboard-image-file-and-cache-echo.md`）：

```text
[+1.802s] changeCount 524 → 526
  types=["public.file-url", …]          ← 图像数据类型全没了
  item[0] fileURL = file:///…/Library/Caches/WeType/dsclp/1789847384202.png
```

- 跳变是 **2** 而不是 1：回写者连写两次，采样太疏只看到净结果。
- 回写发生在 **1.8–2.0 秒后**，且是**覆盖**而非追加。
- 缓存副本与源文件都是 712×448 PNG，但字节 104218 → 69601、**连像素哈希也不同**（回写者重编码时改了像素或色彩配置）——所以任何基于内容的身份都吸收不了这种回写。

## 面板怎么读

每个 `changeCount` 跳变打一行，后面跟该时刻的完整状态：

- `[+Δs]`：相对上一次变化的间隔。毫秒级 = 分步写；秒级 = 别家进程回写。
- `changeCount`：跳变量本身有信息（跳 2 说明中间还有一次我们没采到的写入）。
- `items` / `types`：**类型清单的消失**往往比路径更能说明意图（回写只剩 `file-url`）。
- `fileURL` / `png` / `tiff` 字节数：用来判断载荷到底是文件引用、图像数据，还是两者都有。
