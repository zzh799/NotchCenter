# 服务控制类插件开发指南

> 版本：1.1
> 日期：2026-08-24
> 适用范围：管理单个 launchd LaunchAgent 的"服务控制卡"插件（DshPlugin / CalibrePlugin 模式）。
> 插件通用流程（入口协议、Plugin.plist 登记、构建验证、通用坑）见 [`插件开发指南.md`](插件开发指南.md)，本文只讲服务控制类的专门内容。

---

## 1. 这类插件是什么

一个插件管理**一个** launchd 服务（用户级 LaunchAgent），在抽屉里提供一张控制卡：

- 状态圆点（五态配色）+ 服务标题 + 副标题（运行状态 / 监听端口）
- mini 开关：启停 launchd 服务（`launchctl bootstrap` / `bootout`）
- 点击卡片非开关区：打开服务网页（探测到的端口优先，硬编码 URL 回退）
- 长按 0.2s：弹出独立 NSPanel 浮窗（Launch at Login 开关 / PID / 端口 / 状态 / Restart 按钮）；长按时长、frame 追踪与点击抑制统一由 Kit 的 `blockPopoverTrigger` 提供，不要自写手势

现有实例：

| 插件 | 服务 label | 服务形态 |
|---|---|---|
| DshPlugin | `com.deepseek.dsh-web` | pnpm 包装（`pnpm dsh web`，端口 3080） |
| CalibrePlugin | `com.user.calibre-server` | sh wrapper 等待外置卷后 exec（端口 8080） |

核心模式是**专用插件**（原决策 5）：不做服务扫描、不做通用服务面板。每个服务一个插件，配置硬编码在 `ServiceConfig`，五件套源码复制后改配置与文案。launchd 探测/控制/plist 逻辑**全部复用** `LaunchdControlKit`，插件层不写任何 launchd 代码。两个实例尚可接受复制；若出现第三个同类插件，再评估抽取公共实现（目前刻意不抽，保持各插件独立可删改）。

## 2. 分层架构

| 层 | 位置 | 职责 | 并发模型 |
|---|---|---|---|
| 基础库 | `LaunchdControlKit/`（独立本地包，纯 shell 封装，不依赖 NotchCenterKit） | 探测 / 控制 / plist 读写 | 全部同步阻塞 |
| 插件层 | `Plugins/<Name>Plugin/Sources/`（五件套） | 轮询调度、动作编排、UI | `@MainActor` + `Task.detached` |

原则（原决策 7）：**库同步、插件调度**——Kit 所有 API 同步阻塞（毫秒级 shell 调用），插件必须经 `Task.detached` 丢后台执行，结果回 `@MainActor` 更新 `@Published` 驱动 SwiftUI。

### LaunchdControlKit API 速查

| 类型 | 关键成员 | 说明 |
|---|---|---|
| `LaunchdProbe.Target` | `label` / `plistPath` / `workerPattern` | 服务三要素；`workerPattern` 为 nil 时跳过野进程识别 |
| `LaunchdProbe` | `probe() -> LaunchdServiceStatus` | 四态全量快照（`launchctl list` + `pgrep -f` + `lsof` + `ps`） |
| `LaunchdControl` | `start()` / `stop()` / `restart()` / `setAutostart(_:)` | 副作用操作；start = `bootstrap gui/<uid> <plist>`，stop = `bootout`（幂等） |
| `LaunchdPlist` | `makeContents(...)` / `createIfMissing(contents:)` / `writeRunAtLoad(_:)` | 模板生成（Label / ProgramArguments / RunAtLoad / KeepAlive / WorkingDirectory / EnvironmentVariables / **ThrottleInterval** / StandardOutPath / StandardErrorPath）；已存在不覆盖；只改单字段保留其余 |

### 插件五件套

| 文件 | 职责 |
|---|---|
| `<Name>Plugin.swift` | 主类 `@objc(<Name>Plugin)`；`static var blocks` 声明抽屉块；`attachServices` 里 `createIfMissing` 兜底建 plist；`pluginWasDisabled` 关浮窗 |
| `<Name>ServiceConfig.swift` | 硬编码服务配置（label / plistPath / workerPattern / fallbackWebURL / programArguments / 日志路径 / plist 模板参数） |
| `<Name>ServiceMonitor.swift` | `@MainActor ObservableObject`：轮询（2s 活跃 / 10s 空闲）+ 动作编排（busy 态 + 动作后 600ms 延迟刷新） |
| `<Name>ServiceBlockView.swift` | 抽屉块 UI：状态圆点 / 标题 / 副标题 / mini 开关；卡片壳走 Kit 的 `BlockCard`（悬停 `hoverEffect: true`），点击 + 长按浮窗走 `.blockPopoverTrigger(onTap:onLongPress:)`，不自绘背景描边、不手写手势 |
| `<Name>Popover.swift` | 浮窗内容视图 `<Name>PopoverContentView` + 无状态薄入口 `<Name>Popover`（生命周期 / 外观 / 弹出动画统一走 Kit 的 `BlockPopover`，插件不自己管 NSPanel） |

## 3. 状态机与 UI 呈现

`LaunchdServiceStatus.State` 五态（`LaunchdProbe.probe()` 判定）：

| 状态 | 含义 | 圆点色 | 副标题 |
|---|---|---|---|
| `.stopped` | 未加载且无进程 | 灰 | Stopped |
| `.managed` | launchd 已加载且由它（或其子孙）提供服务 | 绿 | Running · port \<n\> |
| `.loadedNotRunning` | 已加载但未运行（启动中或崩溃） | 黄 | Loaded, not running |
| `.unmanagedExternal` | 有进程监听端口但与 launchd 实例无血缘（野进程） | 橙 | ⚠️ Unmanaged process |
| `.portConflict(n)` | 多个实例同时监听 | 红 | ⚠️ n instances listening |

开关语义（原决策 4）：**只认 `.managed`**。野进程占用端口不算开启——否则服务已停但端口被别的程序占用时开关会误显示为开。

pnpm / sh 包装场景：真正监听端口的可能是 launchd PID 的子孙进程（wrapper `exec` 或多级包装），`probe()` 用 `isDescendant` 沿进程树上溯判定血缘，所以“launchd 管理但 PID 不同”仍算 `.managed`。

## 4. 新增一个服务控制插件：步骤

### Step 0 收集事实（最重要）

读真实 `~/Library/LaunchAgents/<label>.plist` 和它引用的 wrapper 脚本（如有），提取：

- `label`、`ProgramArguments`、`WorkingDirectory`、`RunAtLoad` / `KeepAlive` / `ThrottleInterval`
- stdout / stderr 日志路径（可能分开两个文件）
- 服务端口（wrapper 脚本里的 `--port` 或文档），用于 `fallbackWebURL`
- 进程命令行特征（见 §5）

模板参数必须**照抄真实 plist**——`createIfMissing` 只在 plist 丢失时兜底重建，重建结果应与原文件语义一致。

### Step 1 扩展模板（仅当 `makeContents` 缺键）

给 `makeContents` 加**可选参数带默认值**（加法式改动，现有调用方不受影响），如 CalibrePlugin 落地时加的 `throttleInterval: Int? = nil`。同步在 `LaunchdControlKitTests` 加用例（nil 不写键 / 传值写键）。

### Step 2 复制五件套

从最接近的现有插件整体复制 `Sources/` 五个文件，按 §1 的命名规则改类型名与文件名；改 `ServiceConfig` 常量（Step 0 提取的值）；改三处文案（块标题 / 浮窗标题）与块元数据（id / displayName / symbolName / 支持跨度，默认 `.small` + `.medium`，原决策 11）。

### Step 3 登记与构建验证

按[《插件开发指南》§4](插件开发指南.md#4-新增插件步骤)建目录、写 Plugin.plist（`Dependencies` 写 `["LaunchdControlKit"]` 即可获得与 Dsh/Calibre 相同的依赖与 rpath）、跑构建与冒烟。launchd 类无额外登记项。

### Step 4 测试

复制 `CalibrePluginTests` / `DshPluginTests`：只验证 Config 常量与模板内容（Label / ProgramArguments / RunAtLoad / KeepAlive / ThrottleInterval / 日志路径），**不触碰真实 LaunchAgent**（同 `SystemSleepGuardTests` 约定）。

## 5. workerPattern 选取与野进程判定

`workerPattern` 是 `pgrep -f` 的命令行特征串，用于**缩小**野进程候选；但候选的**定性**由 `LaunchdProbe.resolveState` 决定：野进程 / 端口冲突只认**真正在监听 TCP 端口**的进程，且须与 launchd 实例无血缘。仅命令行特征匹配但未监听的进程——`tail -f` 看日志、编辑器打开 wrapper 脚本、刚 `bootout` 的残留进程——**不参与判定**（CalibrePlugin 落地时曾因宽泛特征串 + 旧状态机，服务未启动误显示 Unmanaged）。

选取规则：

- 写**字面量子串**即可，ERE 元字符由 Kit 的 `escapingERESpecials` 自动转义（"bin.ts web" 的 "." 不会通配）。也因此在配置里写不了正则——选一个稳定的字面子串。
- 优先选**真实二进制路径片断**（如 CalibrePlugin 的 `"MacOS/calibre-server"`），不要用会撞上日志文件名 / 脚本文件名的宽泛子串（`"calibre-server"` 会命中 `tail -f …calibre-server.out.log`）。
- wrapper 等待期（等外置卷的 sh 进程）**无需特征覆盖**：launchd PID 本就在候选里，`exec` 不换 PID。
- 自身及父进程链已由 `isSelfOrAncestor` 排除，不怕宿主 / 终端命令行撞特征。
- 已知边界：手动跑同特征二进制且在监听 → 判为野进程（橙色 ⚠️）——这是预期行为，提醒你有不受管理的实例在跑。

## 6. plist 模板与既有文件的关系

- `attachServices` 的 `createIfMissing`：**已有 plist 永不覆盖**，模板只做丢失兜底。
- 自启开关走 `LaunchdControl.setAutostart`（PlistBuddy 只改 `RunAtLoad`）与 `writeRunAtLoad`（读改写保留其余字段）——用户手改的其他键不会丢。
- 想给已有服务加行为时改真实 plist / wrapper，不要试图让插件“接管改写”plist 内容。

## 8. 常见坑（服务控制类特有）

通用坑（@objc 主类、rpath、UI 字符串语言等）见[《插件开发指南》§6](插件开发指南.md#6-常见坑)；这里只列服务控制类特有的：

- **Kit 调用禁止留在主线程**：`probe()` 一轮要跑 4~6 个 shell 命令，主线程调用会卡 UI；一律 `Task.detached`。
- **浮窗锚定坐标**：SwiftUI `.global` 是左上原点 y 向下，`convertToScreen` 要 AppKit 坐标（左下原点 y 向上），必须先 y 翻转再转换，否则浮窗镜像到屏幕底部（Kit `BlockPopover.present` 内有完整实现，插件不要自己换算坐标）。
- **长按手势用纯 `LongPressGesture`**：不能 `sequenced(before: DragGesture)`——onEnded 会推迟到拖拽阶段结束，浮窗变成松手后才弹出。
- **别只靠 workerPattern 判定野进程**：`pgrep -f` 字面匹配会命中 tail 日志、编辑器打开脚本、bootout 残留等无辜进程；定性必须走“监听 + 血缘”（Kit 的 `resolveState` 已内建，插件层不要绕过它自判状态）。
