## Context(背景与约束)

现状：历史**永不按时间过期**，只按条数（50 条含置顶）与媒体字节预算（200MB）淘汰（见 `Plugins/ClipboardHistoryPlugin/README.md` 的「通用」节）。隐私说明里对应的话术是"介意的话请在复制敏感内容前先暂停记录，或事后一键清空"——把清理责任全推给用户手工动作。

要加的是**周期性自动清理**：档位 `关闭 / 每天 / 每周(默认) / 每月`。

约束与既有机制——

- **历史是插件级全局单例**（`ClipboardHistoryStore.shared`，共识见 [2026-09-05 决策记录](../implemented/2026-09-05-clipboard-history-plugin.md)）。多个放置实例共享同一份历史，所以清理策略**只能是全局一份**，不能按实例设置（否则两个实例各写各的周期，语义直接自相矛盾）。
- **清理动作已经有权威实现**：`ClipboardHistoryLogic.clearingUnpinned` + `commit(_:)`（先落盘再删媒体文件，`commit` 是条目变更的唯一出口）。自动清理必须是它的**定时触发**，不能另写一条删除路径——否则图片文件会变成孤儿。
- **设置入口有两个**（`NotchPanelContent.showPluginSettings`）：块级 `instanceSettingsView` 优先，块未声明时回退插件级 `settingsView`。抽屉块 `clipboard.history` 声明了实例设置（显示条数），库页块 `clipboard.library` 一个都没声明；插件级 `settingsView` 当前是 nil。
- **节拍现状**：store 的 `tickTimer`（1s / 2.5s 轮询）由**可见性**驱动——无放置实例或抽屉不可见就停表（`recomputeTimer`）。清理是"到点就跑"的房间整理义务，不该绑在"用户正看着它"上。
- 应用会被长期挂着（accessory 宿主），也会被退出后隔几天再启——两条路径都要覆盖（进程内定时 + 启动补算）。

**不做**（out of scope）：清理前的二次确认或"待清理"预览（自动清理的意义就是无需交互）；清理结果的通知 / 横幅（历史 UI 里没有通知位，另立决策再谈）；按类型或按来源 App 的差异化清理；把 `maxEntries` / 媒体预算改成可配置；清理频率低于"每月"（如"每季度"）。

## Decision(决策)

**一句话：新增全局设置「自动清理」，四档 `关闭 / 每天(1 天) / 每周(7 天，默认) / 每月(1 个日历月)`；到点即执行与「清空未置顶」完全相同的清理（置顶恒保留），时间戳落盘，进程内低频检查 + 启动补算。**

**D1 — 清理内容 = 全部未置顶条目，置顶恒保留。** 复用 `ClipboardHistoryLogic.clearingUnpinned` 并走 `commit(_:)` 落盘，媒体文件由 `commit` 连带回收。理由：语义与既有「清空未置顶」动作、清空浮层文案（"删除所有未置顶条目？置顶条目会保留"）完全一致，用户不需要学第二套规则；置顶是显式意图，任何自动化都不该动它（与媒体预算"永不淘汰置顶"同一条不变量）。

**D2 — 周期是"清理频率"，不是"保留时长"。** 每周 = 每周清一次（清掉当时全部未置顶），而不是"只删 7 天前的条目"。理由：档位文案是"自动清理：每天/每周/每月"，读作清理动作的节拍最直接；且"保留时长"读法下，一条刚复制的条目在下次到点时也会因为超过周期而被删——两种读法的终态几乎一样，但"频率"读法的中间态可预期（到点即回到只剩置顶的干净状态），也更容易被用户自己验证。此点已向用户征询并拍板。

**D3 — 加「关闭」档，默认档为「每周」。** 四档：`关闭 / 每天 / 每周 / 每月`，`selectable` 顺序即 UI 顺序。默认档位是"每周"（未设置过的新装/老用户按新默认值走，首次到期才清）；「关闭」档让介意默认值的人一键关掉，避免"我什么都没配，历史却被清了"。已向用户征询并拍板。

**D4 — 时间戳口径：首次启用只起算、不立刻清；改档即从此刻重新起算。** 落盘 `cleanup.lastRunAt`。
- 缺失（新装 / 从无此设置的老版本升上来）→ 记 `now`，**不执行清理**。否则升级当天就会把存量历史清掉，属于最坏的意外删除。
- 用户改档 → 记 `now` 并重新起算，**不立刻清**。理由：改档是最容易被"顺手试一下"的操作，任何"改完立刻执行一次"的实现都会变成隐形的删除按钮；代价只是新档位的首次执行晚一个周期。

**D5 — 判定用日历加法，不用固定秒数。** `Calendar.date(byAdding:)`：每天 = `day:1`、每周 = `day:7`、每月 = `month:1`（"每月"按日历月而非 30×86400，跨 2 月 / 跨夏令时才不会漂）；`Calendar` 可注入，测试用固定日历。日历加法返回 nil 的极端情况回落到固定秒数（86400 / 604800 / 2592000）。

**D6 — 到期时间同时比对 `Date`，不依赖定时器"累计"。** 判定 = `now >= lastRunAt + 周期`。睡眠唤醒、系统时间跳变、定时器被 runloop 拖后，全部由这一次比较自然收敛——不引入"多少次 tick = 一天"的脆弱计数。

**D7 — 检查节拍是独立的低频定时器（60s），与可见性 tick 解耦、与 `isObserved` 无关。** 挂在 `attach` → `suspend` 之间：插件启用期间一直跑（哪怕一个放置实例都没有），插件禁用即停。理由：清理是全局房间整理，不该等用户把抽屉打开；60s 一次 `Date` 比较的成本可忽略，且让"到点"最多晚一分钟生效。

**D8 — 两个设置入口都能到达这一项。** 新增插件级 `settingsView`（内容只有自动清理一项），让从未声明设置的库页块齿轮也能进；同时把它作为**全局分节**放进抽屉块的实例设置浮窗（`本组件` / `全局` 两节）。理由：抽屉块是主入口，若只在库页块暴露，不放置库页的用户根本找不到这一项；而清理本身是全局设置，在实例浮窗里用分节标题明确标注作用域即可，不构成"同一入口写两遍"（两个入口指向不同块，屏幕上不会同时出现）。

**D9 — 静默执行，不做确认、不做通知。** 与「清空未置顶」的手工动作不同（那个有浮层二次确认，因为是即时破坏性动作）；自动清理若还要确认就失去意义，若再补一条通知则要在抽屉里新造通知位。改为**在设置说明行里写清后果**（"到点自动清空未置顶条目，置顶条目始终保留；改档后从此刻重新起算"）。

**D10 — 纯逻辑全落 `ClipboardHistoryLogic`，档位定义也在那里。** 档位枚举、`nextDue`、`isCleanupDue`、`sanitize` 都是纯函数，可在无 AppKit 的 Linux 容器测试里断言；`Timer` / `StateStore` / `Date()` 只在 store 层。

## Alternatives considered(备选方案)

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 到点清空全部未置顶（本决策） | 与既有「清空未置顶」语义、文案、实现三者同一；终态可预期（只剩置顶） | 刚复制的条目也会被一起清掉 | **采用**（用户拍板） |
| B. 周期当保留时长（只删超过一个周期的条目） | 新条目一定安全 | 与档位文案的直觉读法背离；终态与 A 几乎相同却多一层"条目年龄"概念；实现要多带 `capturedAt` 比较 | 否决（用户拍板） |
| C. 只有三档，不可关闭 | 严格贴合原始需求字面 | 自动删数据的功能不能关，介意的人只能卸载插件 | 否决（用户拍板加「关闭」档） |
| D. 设置放在实例级（`ClipboardInstanceConfig`） | 复用现成的每实例存储，入口就在抽屉块齿轮里 | 历史是全局的，两个实例可以配成两个周期 → 语义自相矛盾 | 否决 |
| E. 只在插件级 `settingsView` 暴露，不改实例设置浮窗 | 少改一处 UI，无重复行 | 抽屉块是主入口而它的齿轮只开实例设置 → 不放置库页块的用户找不到这一项 | 否决（D8） |
| F. 复用可见性 tick（`poll()` 里顺手比一次时间） | 不新增定时器 | 无放置实例 / 抽屉收起时停表 → "到点"取决于用户有没有打开抽屉，与"自动"矛盾 | 否决（D7） |
| G. 定时器按 `lastRunAt + 周期` 精确排下一次单次触发 | 不靠轮询，一分不差 | 睡眠唤醒后 `Timer` 的触发时机由系统决定、不可靠；仍需 `Date` 兜底比较，等于两套机制 | 否决：只用 `Date` 比较，定时器只负责"定期看一眼"（D6/D7） |
| H. 到期先弹确认 / 清理后弹通知 | 用户对删除有感知 | 自动清理要确认就失去意义；通知要在抽屉 UI 里新造位置 | 否决（D9），改为在设置说明里写清后果 |
| I. 用固定秒数算周期（7×86400） | 不用碰 `Calendar`，测试更简单 | "每月"跨 2 月会漂；跨夏令时的那一周会差一小时 | 否决（D5） |
| J. 首次启用立刻清一次 | "设置立即生效"、无隐藏状态 | 升级当天清掉存量历史 = 最坏的意外删除；试档位也会变成删除按钮 | 否决（D4） |

## Consequences(影响)

- **改动落点**：`ClipboardHistoryLogic.swift`（新增 `ClipboardAutoCleanupPeriod` + `nextDue` / `isCleanupDue` / `sanitize`，纯逻辑）、`ClipboardHistoryStore.swift`（落盘键 `cleanup.period` / `cleanup.lastRunAt`、`@Published autoCleanupPeriod`、60s 检查定时器、`runAutoCleanupIfDue` / `performAutoCleanup` / `setAutoCleanupPeriod`，并把"写回反馈 id 失效即清"提成 `pruneCopyFeedback(keeping:)` 供删除单条与批量清理共用）、`ClipboardHistoryViews.swift`（实例设置浮窗改「本组件 / 全局」两节）、**新增** `ClipboardAutoCleanupSettings.swift`（`ClipboardSettingsSection` + `ClipboardAutoCleanupSettingsRow` + `ClipboardAutoCleanupNote` + `ClipboardPluginSettingsView`）、`ClipboardHistoryPlugin.swift`（声明插件级 `settingsView`）、双语 `Localizable.strings`（新增 8 键，两表键集保持奇偶）。
- **对插件的可见影响**：`clipboard.library` 块**开始出现设置齿轮**（此前无插件级设置，宿主的 `hasSettings` 判定为假）。抽屉块齿轮的内容多出「全局」一节。两处都不改块尺寸与探针（设置浮窗独立于块布局）。
- **数据影响（需用户知情）**：默认档为「每周」，即**不配置的用户也会在起算一周后丢掉全部未置顶条目**。这是 D3 的代价，README 与设置说明行都写明；介意者选「关闭」。
- **持久化**：新增两个插件级键，均为字符串 / 日期标量，不涉及 `history.entries.v1` 的编码契约（`ClipboardEntry` 的向后兼容要求不受影响）；老版本读到新键直接忽略，可回滚。
- **回归面**：既有 `clearUnpinned` 手工动作（共用 `clearingUnpinned` + `commit`，行为不变）、图片文件的孤儿对账（`mediaStore.reconcile`）、实例设置浮窗版式（新增分节与小控件）、库页块齿轮（新出现）。
- **测试**：`ClipboardAutoCleanupTests` 覆盖档位净化、日历到期（含"每月"用日历月）、关闭档永不到期、首次启用只起算不清、到期只清未置顶并落盘、被清图片的媒体文件连带回收、改档重新起算。定时器本身（60s 到点）**不做真时间等待**，只测判定函数与 `runAutoCleanupIfDue` 的注入时间入口。
- **文档**：`Plugins/ClipboardHistoryPlugin/README.md` 的「通用」节"永不过期"表述要改、「设置」节补自动清理四档与作用域说明、隐私说明补一句"周期性自动清理可作为不必手动清空的兜底"。
