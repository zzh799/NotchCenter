# Agent Note: 剪贴板条目悬浮预览

status: implemented
date: 2026-09-20
deciders: 用户（"鼠标悬浮在条目上时，鼠标下方浮动显示该条目的更多内容，如图片显示更大预览，文本显示更多内容"）+ 实现代理
replaces: <无>
superseded-by: <无>

## Context(背景与约束)

现状：条目只有 32×20 的图片缩略图 / 单行截断的文本，要看全貌得长按 → `BlockPopover` 浮窗。长按是**刻意的重动作**，用于"我要看全文并复制"；而"这是哪张图 / 这条是不是我要的那段话"只需一瞥，长按太重。

三条既有机制直接约束实现方式——

- **`BlockPopover` 是进程内单例**（`BlockPopover.shared`），"任一时刻至多一个浮窗在屏"，`present` 会先 `dismiss` 旧窗。悬浮预览若也走它，就会与长按预览抢同一个实例；且每次 `present` 都要建 `NSPanel` + `NSHostingView` + 查一次 `CGWindowList` + 装一次全局鼠标监听——悬浮是高频动作，这个代价不成比例。
- **宿主停留区只认抽屉可见矩形**（`NotchPanelInteraction.isPointInExpandedStayRegion`，可见矩形外扩 10pt），**浮窗窗口不参与**判定；卡片一旦伸出该区域，光标落在伸出部分就等于离开停留区 → 抽屉收起 → `.notchCenterDrawerDidCollapse` 把浮窗关掉。这条正是 `BlockPopover.cardInset` 那段注释在讲的事。
- **块内悬浮控件按既有约定不单列 `BlockProbe`**（[插件开发约定](../../agents/插件开发约定.md)：块内圆角动作按钮默认隐藏、悬停才浮出，落位必然叠在已有探针上，而打包期校验对探针做互不重叠判定）。悬浮预览同族。

**不做**（out of scope）：把组件提进 `NotchCenterKit`（Kit 只加公共 API 的约定，别的插件有需求再另立决策）；悬浮预览上做交互（里面的文字不可选、不可点）；OCR / 图片像素级放大镜；本次不测量它对展开耗时的影响（见 Consequences）。

## Decision(决策)

**一句话：悬浮预览做成块内 SwiftUI overlay，光标停稳 400ms 后从光标下方长出；图片给放大的缩略图，文本给多行，全程不吃点击。**

**D1 — 载体是块内 overlay，不是 `BlockPopover`。** 三条理由对应 Context 的三条约束：零窗口开销（高频动作不该每次建 `NSPanel`）；由构造保证不可能越出块矩形（因而不可能踩"停留区"红线，不需要任何夹紧到抽屉矩形的额外逻辑）；不与长按浮窗抢单例——悬浮预览在屏时用户仍可长按看全。副作用是卡片被块矩形裁切，因此尺寸由块内容盒夹紧（`min(理想尺寸, 盒尺寸 - 边距)`）。

**D2 — 触发是"光标停稳"，不是"进入行"。** 光标在同一行内位移超过 2pt 就重置 400ms 计时；停稳满 400ms 才浮现。理由：跟手浮现会变成闪烁（鼠标扫过列表时逐行长出又收掉），而"停稳才出"正是系统 tooltip 的语义。浮现之后同行内移动只**跟随重定位**、不再重新计时——已经看到的卡片不该因为手抖一下而消失。

**D3 — 卡片长在光标下方，位置夹紧在块内容盒内。** 左上角 = 光标 + (12, 18)；右/下越界则翻到光标左侧/上方。不追求"永不遮挡光标下那一行"——那是悬浮预览的固有代价，移开鼠标即消失。

**D4 — 内容：图片给放大的缩略图（`fit` 不裁切），文本给前 8 行，文件给路径列表。** 图片面积上限 224×140，文本行数按卡片高度定死 8 行、超出省略号。

**D5 — 缩略图长边由 256px 提到 512px，长按预览与悬浮预览改成共用缩略图，原图彻底退出交互路径。** 这是本决策顺带修掉的一处过度设计：上一轮我把长按预览改成读原图，理由是"256px 放大到 256–276pt 在 Retina 下会软"（判断本身没错——256pt 需要 512px 才够 2×）。但悬浮预览是高频路径，为它解一张数 MB 的原图不可接受；而两个预览卡显示尺寸都 ≤ 256pt，512px 的缩略图正好覆盖 2× 需求。所以正解不是"预览读原图"，而是**把唯一的派生图提到够用的大小**：一个文件、一条读取路径、原图只在写回时被碰。代价是缩略图从十几 KB 涨到几十至一两百 KB（50 张最坏十几 MB，在 200MB 预算内），解码后每张约 650KB（缓存容量收到与条目上限一致，最坏 ~33MB，`NSCache` 在内存压力下自行回收）。

**D6 — 不吃点击、不念读屏。** 卡片与容器都 `.allowsHitTesting(false)`：不吃点击是硬要求（否则用户想点下一行会被卡片截胡），且命中穿透后点击仍落在正确的行上。`.accessibilityHidden(true)`：行标签已完整表达内容，读屏再念一遍预览卡是噪音。

**D7 — 收起时机穷举。** 光标离开行 / 行内位移超容差 / 列表内容变化（条目增删、搜索词变化）/ 抽屉收起（`\.isDrawerPresented` 变假，与既有收尾同源）/ 点击写回 / 长按（长按回调里显式取消，否则静止按压会让悬浮卡在浮窗背后同时长出来）/ 该条目已不在列表里（删除后卡片不该留在屏上）。

**D8 — 做成插件本地组件，不进 Kit。** 组件形态对其它插件有复用价值，但 Kit 的约定是只加公共 API；把它提上去等于替所有插件定一个尚未验证的交互，等第二个使用者出现再谈。

## Alternatives considered(备选方案)

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 块内 SwiftUI overlay（本决策） | 零窗口开销；构造上不可能越出块矩形；不与长按浮窗抢单例 | 卡片被块矩形裁切，大图看不全 | **采用** |
| B. 走 `BlockPopover`（与长按同一条路） | 复用既有外观与定位，卡片可超出块 | 悬浮是高频动作却每次建 `NSPanel` + 查 `CGWindowList` + 装全局监听；与长按抢单例；不夹紧就踩停留区红线、夹紧后好处也没了 | **否决** |
| C. 进入行即浮现（无停稳判定） | 少一个状态机 | 鼠标扫过列表时逐行长出又收掉，视觉闪烁；"停稳"才是 tooltip 的既有语义 | **否决** |
| D. 停稳计时在同行内移动时也重置 | 卡片永远长在最后停止点 | 手抖一下卡片就延迟消失，已看到的预览反复闪 | **否决**：改为"浮现前重置、浮现后跟随" |
| E. 预览读原图（维持上一轮的实现） | 像素级真实 | 悬浮是高频路径，为它解数 MB 原图不可接受；而 512px 缩略图已满足显示尺寸的 2× 需求 | **否决**（D5） |
| F. 悬浮预览取代长按预览 | 交互更少、更易发现 | 长按是"看全 + 可滚动 + 可选中复制"，悬浮卡做不到（不可交互）；且会破坏既有习惯 | **否决**：两者分工保留 |
| G. 提进 `NotchCenterKit` | 其它插件可直接用 | Kit 只加公共 API；为一个尚未验证的交互先替所有插件定型 | **另立**：等第二个使用者 |
| H. 给悬浮控件单列 `BlockProbe` | 能被打包期校验覆盖 | 违反既有约定——悬浮控件落位必然叠在已有探针上，会直接判错 | **否决** |

## Consequences(影响)

- **改动落点**：`ClipboardHoverPreview.swift`（**新增**：`ClipboardHoverPreviewModel` 计时模型 + `ClipboardHoverCard` 卡片 + `ClipboardHoverPreviewLayer` 定位层 + `ClipboardHoverCardGeometry` 纯几何 + 命名坐标空间常量）、`ClipboardHistoryViews.swift`（块壳改 `ZStack` 挂浮层并声明坐标空间、行挂 `onContinuousHover`）、`ClipboardLibraryViews.swift`（同款接线：置顶看板卡与最近列表行都要）、`ClipboardMediaStore.swift`（缩略图长边 256 → 512）、两个预览卡从"读原图"改回"读缩略图"、双语 `Localizable.strings`（新增 `hover.file.more`）。
- **一处顺带的结构调整**：抽屉块的长按回调从行视图（`ClipboardRowView`）上移到块视图。原因是"长按前先取消悬浮计时"这条要求——行视图看不到悬浮状态，回调只能由持有它的父层提供。
- **回归面**：长按预览（内容源从原图改为缩略图，512px 下观感需真机确认不回退）、点击写回、行内按钮悬浮（角标按钮与悬浮卡可能同时出现，需确认不遮挡操作）、滚动（见下条）、库页横向看板与纵向列表两种滚动容器。
- **已知粗糙处，必须真机核对**：**滚轮滚动时鼠标不动、内容在动**，悬浮卡可能残留在已滚走的条目上。可用的兜底是"列表内容变化即收起"（条目增删、搜索词/筛选变化都覆盖了），但纯滚动不改 `entries`，所以那一条盖不住——理论上 SwiftUI 会在行视图位移时重算 hover 追踪并投递离开事件，**这一点本轮无法验证**。真机上若不成立，需要另设观测（宿主滚动事件在 `NotchPanelContent.handleDrawerScroll`，插件侧拿不到）。
- **性能**：悬浮预览是新增交互路径，会新增"读一张 512px 缩略图"的一次性成本（缓存命中后为零）。**本轮不做耗时量测**——沿用 `NOTCHCENTER_CLIPBOARD_*` 探针口径若要量，需另设观测点。
- **测试**：`ClipboardHoverPreviewTests` 14 个用例覆盖计时语义（停稳才出 / 浮现后跟随 / 换行重计时 / 超容差重计时 / 容差内抖动不重计时 / 离开即收 / 无关目标的 end 被忽略 / cancel 双重清理）与几何（右下优先、贴边翻转、容器过小则夹住、卡片按容器夹紧）。**真实 hover 事件、Retina 观感、与长按浮窗及角标按钮的实际叠放覆盖不到**，必须在真机核对。
- **文档**：`README.md` 新增"悬浮预览"一节（触发条件、不吃点击、不越出块、与长按的分工）。
