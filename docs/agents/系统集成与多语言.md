# 系统集成与多语言 — 领域约定

> [AGENTS.md](../../AGENTS.md) 的领域子文档：菜单/快捷键、休眠抑制、本地化等跨领域系统集成约定。

## 标准编辑快捷键依赖隐藏主菜单

accessory 应用没有可见菜单栏，程序化启动也没有带 Edit 菜单的默认主菜单，⌘C / ⌘V / ⌘X / ⌘A / ⌘Z 属于菜单键等价物——分发路径是 `keyWindow.performKeyEquivalent` → `NSApp.mainMenu` → nil-target 动作沿响应链落到 NSTextView。`EditMenuInstaller.install()` 在启动时安装这份不可见菜单（应用菜单保留 ⌘Q/⌘H），不要删除或改成给某个具体视图固定 target；否则笔记编辑器等文本输入的复制/粘贴快捷键整体失效（普通输入不受影响，回归见 `EditMenuInstallerTests`）。

## 保持唤醒需要管理员权限

`SystemSleepGuard` 通过 `osascript with administrator privileges` 调用 `pmset disablesleep`。**不要在单元测试里触发真实休眠抑制**；测试只验证命令字符串与 shell 语法（见 `SystemSleepGuardTests`）。

## 系统权限要诚实（日历 / 提醒 / 摄像头 / 屏幕录制 / 辅助功能 / 定位 / 照片图库）

权限清单、四态语义与跳转 URL 在 Kit 的 `SystemPermission`；宿主侧唯一门面是 `PermissionCenter`，「权限管理」弹窗是 `PermissionGuidePanel`。决策背景见 [`2026-09-11-permission-management-panel`](../agent-notes/implemented/2026-09-11-permission-management-panel.md)。四条红线：

- **缺权限只改变呈现，不改变可用性**：插件块在未授权时整块（或局部）切换为引导态，但**绝不抛错、绝不整页失败**，宿主其余功能不受影响。降级是每个需要权限的插件自己的义务。
- **系统授权窗的触发点只有一处**：插件不自行调 `requestAccess`，一律经 `HostController.presentPermissions(_:)` 弹权限管理窗，由用户在窗内显式点击发起请求——链路唯一、可审计，也避免插件在后台悄悄弹系统窗。
- **启动/装载期零 TCC 触发**：`AVCaptureDeviceInput(device:)`、`AVCaptureSession.startRunning()`、`SCShareableContent`、`CGRequestScreenCaptureAccess()`、`AXIsProcessTrustedWithOptions(prompt:)` 在未授权时一被调用就会弹系统窗，所以采集/抓帧对象一律**后移到"用户真的要用"的时刻**构造，前面加只读判定（`CGPreflightScreenCaptureAccess` / `authorizationStatus`）。`attachServices` 装载期（= 每次启动 App）尤其不允许——那正是"每次一打开就请求权限"的来源。同理 `NSWorkspace.open(SystemSettingsURL…)` 只允许出现在权限弹窗的行内按钮，插件不代开系统设置（决策见 [`2026-09-11-permission-lazy-trigger`](../agent-notes/implemented/2026-09-11-permission-lazy-trigger.md)）。
- **查询与请求必须分开**（`PermissionStatusProviding` / `PermissionRequesting`）：查询同步无副作用，请求会弹窗。单测只注入查询侧的假实现，**绝不触发真实授权窗**。
- **授权后需重启的要明说**：屏幕录制（`replayd` 缓存）与辅助功能（进程级 AX 缓存）在授权后**必须重启 App** 才生效（`SystemPermission.requiresRelaunch`）。UI 不写这句，用户就会以为"授权了但没用"。

权限清单与 `Resources/Info.plist` 的用途字符串键必须一一对应（`PermissionTests` 校验）；屏幕录制与辅助功能的 TCC **不读**用途字符串，故这两项 `usageDescriptionKey` 为 nil、只做跳转引导。

**新增一项权限要同步四处**（缺一处就半生效或门禁红）：Kit `SystemPermission` 的 case + 四个穷举 switch（`privacyPane` 的 TCC 锚点、`usageDescriptionKey`、`symbolName`、`requiresRelaunch`）、`Resources/Info.plist` 的用途字符串、宿主 `PermissionCenter` 的 `status(of:)` / `request(_:)` 两个分支、宿主两张 `Localizable.strings` 的 `permission.name.<rawValue>` 与 `permission.purpose.<rawValue>`。`PermissionGuidePanel` 按 `allCases` 自动多出一行，卡片高度要同步抬高（行容器可滚动，尺寸偏小只是末行需要滚一下）。新增 case 会升 `NotchCenterKitAPI` 次版本并立 api-changelog：对**穷举 `switch SystemPermission`** 的第三方插件是源码级破坏（补 `@unknown default` 即免疫）。

**照片图库（`.photos`）**：消费方是相册插件 `AlbumPlugin`。PhotoKit 没有"纯读"授权级别，读图库只能走 `.readWrite` 档；`PHAuthorizationStatus.limited`（用户只授权部分照片）在宿主侧**并入已授权**——Kit 四态没有受限档，而受限选集确实可读，判成不可用会把可用功能锁死，取不到图的情形由插件自己落到"取图失败"降级态。查询（`authorizationStatus(for:)`，无副作用、不弹窗）与请求（`requestAuthorization(for:)`）都在 `PermissionCenter`，插件只调 `presentPermissions([.photos])`。

**屏幕录制的参考实现是 `LidAngleDepthPlugin`**（合盖透视效果，[决策](../agent-notes/implemented/2026-09-11-lid-angle-depth-effect.md)）：它是屏幕录制的首个消费方，也是"两档降级"的样板。要点：`start()` 在无权限时**直接返回**（不预热、不抓帧，预热会枚举窗口 `SCShareableContent`，那正是触发点）；实时流不可用时退化为合盖瞬间的单帧静图而不是整页报错；抽屉块与设置页只在真的缺权限时给引导按钮。另注意该插件依赖可复用动态库 `Plugins/LidAngleKit`（盖角传感器，**无权限依赖**）。

## 私有框架访问（dlopen / dlsym / 借 com.apple.* 进程）

系统没有公开 API 时用 `dlopen`/`dlsym` 惰性解析私有符号，是本仓允许的做法（先例：`MediaControlsPlugin` 的 `MediaRemoteBridge`、`DisplayPlugin` 的 `IOAVServiceBackend`）。四条约定：

- **单点接触面**：一个插件内只允许一个文件负责私有符号解析与调用约定，符号名、字典键、命令值全部集中在这一处，其余代码只依赖它的类型化接口。系统更新导致符号漂移时单点适配，不牵连业务代码。
- **惰性 + 可降级**：符号解析失败即整体不可用（组件切空态），**不允许崩溃或断言**；`dlopen` 句柄首次使用时缓存，不在启动/装载期解析。
- **不新增 entitlement / 用途字符串**：宿主无沙盒、ad-hoc 签名（`Project.swift` 的 `CODE_SIGN_IDENTITY = "-"`，全仓无 `.entitlements`），私有框架调用不落 TCC，因此不需要权限引导，也不要往 `Resources/Info.plist` 加用途字符串。
- **实测优先，且要确认测的是谁**：私有框架的可用性结论必须在本机跑通再写进决策，并且要交代**读取方进程的身份**——见下面那条教训。

### 教训：`swift -e` 不是可信探针（2026-09-28 踩过）

判断「本进程能不能读某个私有框架」时，**不能用 `swift -e` 当被测进程**：它是被 Apple 签名的 `com.apple.dt.swift-frontend` 在跑，恰好满足只放行 `com.apple.*` 的那类检查，于是会给出「能读」的假阳性。当天据此得出「NotchCenter 可以直连 MediaRemote」的结论是错的，写进决策记录后才被更严格的复测推翻。

可信做法：**编译一个独立二进制或直接跑目标 `.app`** 再测。

### MediaRemote 的现状（2026-09-28 复测，macOS 15.7.5）

macOS 15.4 起系统**只放行 bundle id 以 `com.apple.*` 开头的进程**访问 MediaRemote，社区说法属实。同一份读取代码，按读取方进程身份实测：

| 读取方进程 | bundle id | 结果 |
|---|---|---|
| `/usr/bin/perl` + helper 动态库 | `com.apple.perl` | ✅ 读到曲目 |
| `swift -e` | `com.apple.dt.swift-frontend` | ✅ 读到（**假阳性，见上**） |
| `swiftc` / `clang` 自编译二进制 | 自签名 | ❌ 空 |
| 自建 `.app` | 自定 bundle id | ❌ 空 |
| NotchCenter.app 内直连 | `com.notchcenter.*` | ❌ 空 |

兜底（也是唯一可行的）路线：**把调用点搬进 `/usr/bin/perl` 进程**，由它加载一个 helper 动态库代跑查询，结果写 stdout 给宿主读。本仓已按此路线落地：源码 vendored 在 `Vendor/mediaremote-adapter`（BSD-3，见该目录 `VENDORED.md`），`scripts/build.sh` 用 clang 编成 framework 并随白名单插件（`BRIDGE_PLUGIN_IDS`）分发到 `Contents/Resources/Bridge/`；插件内的唯一接触面是 `MediaRemoteBridge`。

其他私有框架（如 `DisplayPlugin` 用的 `IOAVService`）目前不受这条只放行限制，仍是进程内直连——**不要因为 MediaRemote 的例子就给所有私有框架都套一层 bridge**：判定依据始终是"按上面的可信探针实测结果"，不是"另一个框架也踩过坑"。

## 多语言（en / zh-Hans）

所有面向用户的字符串一律走本地化表，不许硬编码。机制是 Apple 原生 `.lproj` + `Localizable.strings`，每个模块自带翻译：

- 宿主用 `L()`/`LF()`（`Sources/NotchCenter/Localization.swift`，资源经 SPM 打进 `NotchCenter_NotchCenter.bundle`）；
- 插件用各自 Sources 里的 `L()`/`LF()`（基于 Kit 的 `L10n.string` + `Bundle(for:)`）；
- 插件的显示名/描述双语写在各 `Plugin.plist` 的 `DisplayNameLocales` / `DescriptionLocales` 字典（build.sh 生成 InfoPlist.strings）。

en 是基准键集，zh-Hans 必须保持键集合一致（`LocalizationTests` 强制校验）。语言跟随系统，设置面板可覆盖（写 AppleLanguages，重启生效）。品牌名（DSH、Calibre、OpenCode、Zen）不翻译。

注意 `L10n.string` 故意没有 CVarArg 变参重载：带参数的格式化必须在调用方自己模块内完成（`String(format:arguments:)`），变参跨动态库镜像转发会偶发段错误。
