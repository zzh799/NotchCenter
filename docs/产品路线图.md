## 0. 结论

工程内核已完成,**缺口集中在生命周期后半段**——产品送不到用户手上,也留不住用户。当前的瓶颈不是功能数量,而是交付。

三条最硬的结论:

**发布通道已断 10 天。** 最近 20 次 workflow 运行全部失败(`发布 macOS 应用` 与 `docs-gate` 双红),最后一次成功的发布构建停在 2026-09-10,此后 28 个提交未触达用户。根因是两处结构性故障,与代码质量无关(见 §1.1)。

**分发不可信。** 无 Developer ID 签名、无公证、无自动更新,用户首次启动被 Gatekeeper 拦截,且装上之后再无升级路径。

**生态缺法律与隔离地基。** 无 LICENSE 文件,无插件分发渠道,插件与宿主同进程且不校验签名。

因此本路线图的排序原则是:**先恢复交付,再建立可信分发,最后铺生态地基。功能补齐放在最后。**

## 1. 现状基线

本节只记录可复核的事实与证据,评估结论见后续里程碑。

### 1.1 交付链路故障

| 症状 | 根因 | 证据 |
|---|---|---|
| `release` 每次推送必红 | 硬件依赖用例进了 CI 套件:断言语义为「本机存在盖角传感器」,runner 上必然失败 | [LidAngleKitTests.swift](../Tests/NotchCenterTests/LidAngleKitTests.swift) |
| `docs-gate` 每次推送必红 | 治理清单把 `.git/hooks/pre-commit`、`.git/hooks/commit-msg` 列为必需产出物,而 CI 的干净检出中永远不存在这两个文件 | [manifest.json](../.doc-driven-dev/manifest.json) + [verify-scaffold-manifest.sh](../scripts/verify-scaffold-manifest.sh) |

两处都不是代码回归。第二处是**门禁自锁**:本地必过、CI 必红,差异恰好就是 `.git/hooks` 的存在性。本条也在说明一个更普遍的问题——**项目的质量门禁只覆盖文档,没有任何 PR 级的编译与测试门禁**([docs.yml](../.github/workflows/docs.yml) 只跑文档脚本,[release.yml](../.github/workflows/release.yml) 仅在 push `main` 后运行),因此坏代码可以先合入 `main`,直到发布阶段才暴露。

补充事实:线上 `latest` Release 的附件时间为 2026-09-18,晚于当天失败的流水线运行,应属手工补传而非流水线产物。

## 2. 里程碑

每个里程碑给出目标与验收标准。验收标准是可判定的结果,不是工作量描述。

### M0 恢复交付

目标:让 `main` 上已经完成的功能真正到达用户。

| 编号 | 动作 | 验收标准 |
|---|---|---|
| M0-1 | 解除门禁自锁:把 `.git/hooks/*` 在治理清单中标为本地专属,或让校验脚本按 `git-common-dir` 解析、在 CI 中跳过该项 | `docs-gate` 在干净检出上通过 |
| M0-2 | 隔离硬件依赖用例:为盖角传感器相关用例加环境守卫或 `XCTSkip`,与本项目[测试指南](agents/测试指南.md)「单测不真实触达硬件与系统」的纪律一致 | 无传感器的机器上 `./scripts/build.sh test` 通过 |
| M0-3 | 补 PR 级 CI:新增编译与测试 job | 任何 PR 在合入前都有编译与测试结论 |
| M0-4 | 补 `LICENSE`(仓库根) | GitHub 能识别许可证;第三方开发者明确能否依赖 `NotchCenterKit` 与商用 |
| M0-5 | 恢复发布:修复后重跑,把积压提交交付出去 | `latest` Release 附件时间等于最新 `main` 构建时间 |
| M0-6 | 对齐文档:修正 README 的插件数量与清单、紧凑槽位描述、官网表述;修正架构文档状态头 | 与 [Plugins/](../Plugins) 实际内容及架构文档相互一致 |

### M1 分发可信

目标:用户能无摩擦安装,并能持续升级。

| 编号 | 动作 | 验收标准 |
|---|---|---|
| M1-1 | Developer ID 签名 + Apple 公证(构建脚本已预留 `SIGN_IDENTITY` / `NOTARY_PROFILE`) | 全新机器首次打开无 Gatekeeper 拦截提示 |
| M1-2 | 引入自动更新机制(Sparkle 或自研) | 旧版本可原地升级,无需手动重新下载 |
| M1-3 | 通道分离:稳定通道与预览通道 | 普通用户不会自动拿到 `main` 的 head 构建 |
| M1-4 | 规范版本号(现 [Info.plist](../Resources/Info.plist) 恒为 `1.0.0`)并补 `CHANGELOG.md` | 版本号随发布递增;发布说明为用户可读内容,而非构建号 |
| M1-5 | 崩溃可见:本地落盘崩溃信息并提供主动上报入口 | 线上崩溃可被收集与定位 |
| M1-6 | 提供 Homebrew cask 或等效的一键安装方式 | 一条命令完成安装 |

### M2 生态地基

目标:让第三方开发者敢写、能发,让用户装得安全。这是「插件宿主」这一产品定位的立足点。

| 编号 | 动作 | 验收标准 |
|---|---|---|
| M2-1 | 插件脚手架:一键生成插件工程(目录结构 + `Plugin.plist` + 入口骨架) | 不了解宿主源码的开发者能跑通一个最小插件,流程见[插件开发指南](插件开发指南.md) |
| M2-2 | 隔离与信任模型:针对现行「不沙箱(决策 16) + 不校验签名(决策 30)」,至少引入分级——签名提示、来源标识、API 能力声明 | 安装来源不明的 `.bundle` 时,用户被显式告知风险 |
| M2-3 | API 弃用策略:明确 `NotchCenterPluginAPIVersion` 的弃用窗口与兼容承诺 | API 变更前存在可预期的弃用期 |
| M2-4 | 插件分发:提供插件索引或清单站点,而非只能手动拖 `.bundle` | 用户可从一处发现并安装第三方插件 |
| M2-5 | 插件调试支持:插件日志与故障隔离(插件异常不拖垮宿主) | 插件崩溃时宿主存活且可诊断 |

### M3 功能补齐

原则:每加一个页面先问「它是否值得占用 9 页里的一页」,判定顺序沿用[调研](插件页面选题调研.md) §1.3。排序如下:

1. **恢复 MediaControls**:竞品全员标配,且是「音乐中心页」的前置依赖。**已于 2026-09-28 落地**([决策](agent-notes/implemented/2026-09-28-media-controls-plugin-restore.md)),尚余「音乐中心页」本体。
2. **AI 编码助手监控页**:调研中战略价值最高的一条,也是竞品最难追的差异化方向。
3. 控制中心开关页、天气页:补齐竞品标配项。
4. 其余页面化的推进与否,取决于 §5 决策 D1 的结论。

## 3. 边界与纪律

功能侧的「不做清单」沿用[调研](插件页面选题调研.md) §6,本文件不重复。本路线图新增三条纪律:

**M0 关闭前不再新增官方插件。** 当前瓶颈是交付而非功能数量,继续堆功能只会扩大未交付的积压。

**门禁与实现同源演进。** 任何门禁脚本的产出物假设,都要在干净检出环境中验证一次,避免再次自锁。

**用户可见的声明必须存在。** 申请日历、提醒、摄像头、屏幕录制权限的应用需要有隐私说明;分发二进制的项目需要有许可证。二者当前均缺失。

## 4. 与选题调研的关系

[插件页面选题调研](插件页面选题调研.md) 回答「做什么功能」,本文件回答「怎么把产品交付出去」。两者是互补关系,冲突时有两条优先级规则:

**交付优先于功能。** 当资源有限时,M0 与 M1 优先于 M3 的全部候选。

**调研的 P0 清单在 D1 拍板前处于挂起状态。** 因为该清单的技术载体已被撤销,直接按原文执行会产生「按计划做完却发现形态不成立」的返工。
